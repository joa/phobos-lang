A persistent kernel launches only as many CTAs as the card can run at the
same time, and each CTA loops over the work instead of owning one tile of it.
Because every CTA is resident, they can wait for each other with
`grid_barrier`, and several stages of a computation can run in one launch.

```text
@persistent
@persistent(BLOCKS)
```

With an argument, a literal or an `@autotune` constant, it also compiles the
grid's block count in: `ctx.blocks.x` is that constant, and the launch must
use it. See the [Attributes](/docs/reference/spec/#attributes)
table and `grid_barrier` under
[Indexing and synchronization](/docs/reference/spec/#indexing-and-synchronization)
in the spec.

## What it promises

`@persistent` is a contract with the host: the grid must be co-resident. A
CTA that is still waiting for a multiprocessor never reaches a
`grid_barrier`, and every CTA already at the barrier waits for it forever.

The launcher sizes the grid from the CUDA occupancy API, as the number of
CTAs that fit on one multiprocessor times the number of multiprocessors
(`phobos_kernels::launch::persistent_grid`). Shared memory usually bounds
that number, so the query is made with the kernel's thread count and its
dynamic shared bytes. [Kernel ABI](/docs/reference/abi/#persistent-kernels)
shows the launch from the host's side.

## A minimal kernel

The same stage runs `STEPS` times over a buffer, each pass separated by a
grid barrier. Every CTA strides the whole row, since the grid is sized by the
card and not by the data:

```phobos
@launch(256)
@persistent(BLOCKS)
@autotune(TILE in [1024], STEPS in [16], BLOCKS in [48])
kernel staged(X: tensor<f32>[M, N]) {
  let p = ctx.block.x
  for s in range(0, STEPS) {
    for t in range(p * TILE, N, ctx.blocks.x * TILE) {
      var x = X[0 :+ 1, t :+ TILE]
      X[0 :+ 1, t :+ TILE] = x * 1.0000001 + 0.000000001
    }
    grid_barrier()
  }
}
```

`BLOCKS` is the grid size the host launches with, and `ctx.blocks.x` is that
constant here. The launch appends the barrier word after `X`.

## `grid_barrier`

`grid_barrier()` makes every block of the grid wait for every other, and
orders memory across it: every block's global writes before the barrier are
visible to every block after it. One stage can therefore read what another
block wrote in the stage before. It keeps its state in a barrier word the
launch appends as the kernel's last parameter. `grid_barrier(bar)` names that
word as a parameter of its own instead, and works outside `@persistent`. It
requires:

| Requirement | Note |
| --- | --- |
| The word is an `i32` `[2, 1]` column, or `bar` a named `i32` tensor of at least 2 elements | One slot counts arrivals, one releases the waiting blocks. |
| It is zeroed once before the launch and not shared by concurrent kernels | The barrier keeps its state in it across uses. |
| A one-dimensional grid | |
| Every block reaches the call | A block that skips it leaves the rest waiting. |
| The grid is co-resident | What `@persistent` declares. |

## Interactions

- [`@dynshared`](/docs/attributes/dynshared/): the dynamic shared bytes enter
  the occupancy query, so a larger footprint means fewer CTAs in the grid.
- [`@aligned`](/docs/attributes/aligned/): a broken promise on a dynamic
  dimension traps the CTA that checks it. In a persistent kernel with
  `grid_barrier`, the other CTAs then wait at the barrier for good.
- [`@launch`](/docs/attributes/launch/): the thread count enters the
  occupancy query as well.
