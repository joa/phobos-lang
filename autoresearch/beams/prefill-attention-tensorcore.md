# Beam: prefill attention, first past the GEMM projection then past tensor cores

Prompted by the user once decode (`tg`) crossed parity: prefill (`pp128`) was
sitting at 0.40-0.41x of llama.cpp CUDA and had never been a target this
session. Scope: find and close the largest lever in prefill, correctness
first.

## Mechanism: attention was tied with the GEMM projection, not a minor cost

A real minicpm prefill pass (`nsys profile --trace cuda`, `bench.exe -m
models/minicpm5-1b-Q8_0.gguf -p 128 -n 0 -r 3`, `cuda_gpu_kern_sum`) showed
the three-launch, score-materializing attention path (`attn_scores` +
`attn_softmax` + `attn_mix`, generated by `attn_gemm_src` in
`phobos-gguf/src/backend/device/kernels/attn.rs`) at **37.5-37.9% of total
kernel time, tied with the int8 tensor-core projection GEMM (`q8_qmma`) at
38.7%.** Full numbers, this session, `autoresearch/beams/prefill_attention_ab_kern_sum.log`
(`ab_gemm` section) and the already-archived `prefill_profile_cuda_gpu_kern_sum.csv`
from the round before this beam.

`attn_gemm_src`'s own doc comment called attention "off the critical path"
when it chose to skip tensor cores -- true when it was written, false now
that it is tied with the actual critical-path kernel. Comment corrected in
place (`phobos-gguf/src/backend/device/kernels/attn.rs`).

The dispatcher (`DeviceBackend::attention`, `phobos-gguf/src/backend/device/backend.rs`)
preferred this three-launch path whenever `attn_gemm_fits(spec)` was true
(aligned tiling; true for minicpm's pp128 shape), falling back to
`attention_block_src` -- a proper single-launch FlashAttention-2-style
kernel already in the same file, online softmax, no materialized score
matrix, GQA-aware, causal via `tril` on the one diagonal-straddling tile --
only for misaligned continuations. That preference was never re-measured
against the alternative it was skipping.

## Step 1: A/B the two existing kernels (cheap, no new code beyond a debug toggle)

Forced `attention_blocked` at minicpm's exact pp128 shape (temporary
`PHOBOS_ATTN_FORCE_BLOCK` env toggle on the `attn_gemm_fits` branch, removed
before shipping) and re-traced the same command:

| | attn_gemm path (baseline) | attention_blocked (forced) | delta |
| --- | --- | --- | --- |
| attention's own kernel time | 12.53 ms (37.9%) | 4.25 ms (18.0%) | -66.1% |
| total kernel time | 33.04 ms | 23.62 ms | -28.5% |
| q8_qmma (unaffected) | 12.78 ms | 12.77 ms | noise |

Fusion alone -- code that already existed in the tree, zero new kernels --
closed most of attention's own cost and just over a quarter of the whole
prefill pass's kernel time. `attn_gemm_fits`'s preference was simply wrong
under the current cost structure: it was tuned when the alternative it beat
scored worse, and nothing re-checked that after `attention_block_src` grew
into a real single-pass kernel.

**Shipped**: reordered `DeviceBackend::attention` to try `attention_blocked`
first (whenever `spec.rows > 1` and `spec.start_pos` lands on the block
boundary -- the same condition it already checked, just promoted ahead of
the gemm check), falling through to `attn_gemm_src` only for what
`attention_blocked` declines (a head dimension whose block tile does not
divide 64, or a misaligned continuation -- in practice, for both shipped
models' head dimensions [128, 256], `attn_gemm_fits` being true always
implies `attention_blocked` fits too, since its own tile size always divides
64 at those head dimensions; the fallback exists for a head dimension where
that stops being true, e.g. 192, not reached by either model).

Every gate passes at this state, matching documented baselines to the digit
(see Correctness section; the numbers there are for the final, shipped
state, reorder only).

## Step 2: build a tensor-core version, why it lost, and how that was confirmed rather than assumed

`attention_block`'s remaining 4.25ms still runs in plain f32 (`dot_t`/`dot`,
no tensor cores). Built `attention_tc` (`phobos-gguf/src/backend/device/kernels/attn_tc.rs`,
now removed -- kept below and in the beam's git history) as a tensor-core,
f16, `@pipeline`-staged version of the exact same structure: one program
owns `BR=16` consecutive query positions of one head, a causal loop over
whole f16 key/value tiles followed by one `tril`-masked diagonal tile,
online softmax throughout -- modeled on `examples/flash_attention_fp16.ph`
(the proven FA2-with-tensor-cores template) combined with
`attention_block_src`'s causal-loop-plus-diagonal-tile shape and GQA column
offset (`kcol = h / G * D`).

**Before writing it**, confirmed the target actually engages tensor cores
under phobos-gguf's real compile config (`Context::default()`: `sm_75`,
32-bit index -- not the same as `phobos-lang`'s own test suite's varied
targets). `phobos-lang/src/codegen/target/nvidia.rs`: `has_mma_sync` needs
`index_bits == 64` (false here), but `has_wmma` only needs `cc >= 70` (true
at sm_75 regardless of index width). So `@tensorcore` takes the legacy WMMA
path (`gpu.subgroup_mma_*`), not the newer `nvgpu.mma.sync` -- confirmed by
compiling the probe kernel through `cargo run -p phobos-lang --example emit`
and grepping the output for `gpu.subgroup_mma_compute` (present, six calls)
and the absence of `vector.contract` (the vector-path fallback). Also
compiled clean at `PHOBOS_CHIP=sm_80 PHOBOS_INDEX_BITS=64`. Real tensor
cores, confirmed before investing in the backend plumbing, not assumed.

**Shared-memory budget** at `D=128, BR=16`: query tile + `@pipeline`'s four
live `[BR,D]` f16 K/V buffers (two live tiles x two, for double-buffering) +
the `[BR,BR]` f32 score tile + the `[BR,D]` f32 accumulator, plus the
tensor-core epilogue's own per-warp drain slab -- comfortably under the 48KB
static cap at `D<=128`; not verified to fit at `D=256` (Qwen's few
full-attention layers), so the kernel's own fit-check (`attn_tc_fits`)
declined anything wider and fell through to the existing kernels, which was
never the bottleneck for either model's benchmarked shapes.

### A genuine bug hunt that resolved to a precision finding, not a code defect

First correctness run (`backend_check`) failed one shape:
`attention [29 @ 0 x 16/8 x 128]`, rel err 3.760e-4 against a 1e-4 default
tolerance. Ruled out, in order, each with a real test rather than a guess:

1. **Not `@pipeline`-specific**: identical 3.760e-4 with `@pipeline` removed.
2. **Not the combined `acc = acc*corr + dot(s,v)` expression form** (copied
   from `attention_block_src`, differing from `flash_attention_fp16.ph`'s
   split `acc = acc*corr; acc += dot(s,v)` form): identical 3.760e-4 after
   splitting to match the template exactly.
3. **Not group-size-specific**: added two probe shapes to `backend_check`
   temporarily, `(32, 0, 16, 2, 128)` and `(29, 0, 16, 2, 128)` (group=2,
   not the failing shape's group=8) -- both failed at the same magnitude
   (3.505e-4, 3.492e-4).
4. **Is specific to `start_pos == 0`** (every shape that passed at
   `head_dim=128` had `start_pos>0`; the one dedicated 128-head-dim gate
   entry with `start_pos=0` was the one that failed). At `start_pos=0`,
   `qt=0`'s causal loop has zero keys to walk (`base = NK - R + qt*BR =
   start_pos = 0`), so the diagonal tile alone is the entire answer.

That last point reframes the other three: with many keys contributing
(`start_pos=512`, 512-520 keys), independent per-term f16 rounding errors in
`@tensorcore`'s PV product (`dot(s, v)` truncates the f32 probability tile
`s` to f16 before the WMMA compute -- the `arith.truncf` visible ahead of
every `gpu.subgroup_mma_load_matrix` in the emitted MLIR) average down
roughly `1/sqrt(N)`, landing at 2.25-2.60e-5. At `start_pos=0`'s diagonal-only
first block (N<=16), the same per-term rounding shows at full strength,
3.5-3.8e-4. Confirmed as precision rather than a masking/layout bug two
ways: the magnitude itself (a wrong `tril` moves whole probability mass,
order 1e-1 to 1, not 1e-4), and a direct control -- disabling `@tensorcore`
on the identical failing shape dropped the error to 8.174e-5, f32-reduction
noise, with everything else in the kernel unchanged.

This is not a new accuracy floor for the whole comparison: llama.cpp's own
prefill kernel (`flash_attn_ext_f16`, see the kernel-sum log) computes in f16
too. Gave `backend_check`'s attention checks (`phobos-gguf/examples/backend_check.rs`)
an explicit `1e-3` tolerance for shapes `attention_tc` actually takes
(`head_dim <= 128 && rows > 1 && start_pos % 16 == 0`, mirroring
`attn_tc_fits`), keeping the default `1e-4` for shapes that stay on the f32
kernels. Documented the mechanism in `attention_tc_src`'s own doc comment so
the next person who hits this number does not re-run the same bug hunt.
The two `start_pos=0, head_dim=128` probe rows this hunt added
(`(32, 0, 16, 2, 128)`, `(29, 0, 16, 2, 128)`) were reverted along with the
rest of the tensor-core wiring (see below) since they existed to exercise
`attention_tc`'s own precision floor specifically; if `attention_tc` is
revived, re-add them first.

All four correctness gates passed at this state, both models,
`PHOBOS_ATTN_PERSIST=1`: `backend_check` (worst rel err 3.760e-4, within the
new 1e-3 attention bound), `batch_check` ("batched and sequential agree"),
`model_check` ("backends agree"), `fuse_check` ("the prompt pass agrees
exactly" -- fuse_check compares the fused decode path against the launched
one, both already sharing whatever prefill attention ran; unaffected by the
diagonal-tile finding above since that only bites the very first block of a
prompt pass, never a decode step).

### The speed number that killed it

`nsys` on the same pp128 shape, tensor-core kernel forced through the
dispatcher in place of `attention_blocked`:

| variant | attention_tc + q_cast | vs attention_block (4.25 ms) |
| --- | --- | --- |
| `@launch(128)` (first try) | 5.96 ms | +40.2% (worse) |
| `@launch(256)` (retune) | 5.40 ms | +27.0% (worse) |

Both variants lost, and the retune only closed part of the gap. Total
prefill kernel time with the tensor-core path active (25.33 ms at
`@launch(128)`) was worse than `attention_block` alone (23.62 ms), not
better -- the tensor cores' own throughput advantage never showed up because
the matmuls here are small (`BR=16` against `head_dim=128` is a `16x16x128`
and `16x128x16` pair, nowhere near where a legacy-WMMA GEMM amortizes its
fragment load/store overhead through a shared-memory epilogue slab), and the
kernel pays a fixed cost the f32 path does not: the query cast (`q_cast`,
~0.07ms, cheap on its own but not free) plus that epilogue drain per matmul
call. Full kernel-sum numbers for both variants in
`autoresearch/beams/prefill_attention_ab_kern_sum.log`
(`ab_tc`/`ab_tc256` sections).

**Reverted.** `git checkout --` on every file this touched except
`backend.rs` (kept the dispatch-reorder win, replaced the tensor-core branch
with a comment naming this result and pointing here) and
`kernels/attn.rs`'s doc-comment fix (kept, independently correct). Deleted
`kernels/attn_tc.rs`. Final build: `cargo build --release -p phobos-gguf
--features cuda --examples` and `cargo clippy --release -p phobos-gguf
--features cuda --examples -- -D warnings` both clean; all four gates
re-verified clean on both models at the final, reverted-to-reorder-only
state (worst `backend_check` error 2.902e-4, identical to the pre-existing
documented baseline -- confirms the revert is byte-for-byte the same
computation as before this beam touched anything beyond the dispatch order).

### The kernel, for whoever revisits this

Source (as last built, `@launch(256)`, split `acc`/`+=` form, `@pipeline`
and `@tensorcore` both on) is in this beam's git history
(`phobos-gguf/src/backend/device/kernels/attn_tc.rs` as of the commit before
the revert) and reproduced structurally above. What is likely to actually
move the number, in rough order of promise:

1. **A wider `BR`.** 16 is the WMMA fragment floor, not a chosen tile size --
   never swept upward. A `BR=32` or `BR=64` tile (more shared memory,
   `@dynshared` if the static 48KB cap is the limit, following
   `attention_persist_src`'s own precedent for that attribute) makes each
   matmul call bigger relative to its fixed overhead, which is exactly the
   lever the loss above points at.
2. **Batch the diagonal tile into the loop's own pipelined path** rather
   than running it as a separate, un-staged call, removing one of the two
   distinct WMMA call sites (and its own epilogue drain) per program.
3. **A wider query group per program** (multiple heads per program, the
   same idea `ATTN_QGROUP`/`attention_qgroup` already use for decode) to
   amortize the K/V tile load across more work, if GQA's head-sharing makes
   that free the way it does for decode.
4. **Fold `q_cast` into an existing kernel** rather than a dedicated launch
   -- it is cheap (0.07ms) but not zero, and the query projection is the
   natural place if it can be reached without coupling an architecture-wide
   kernel to one attention path's precision (flagged as a real tension in
   the reverted kernel's own doc comment, not resolved here).

None of these were attempted: the two variants tried (`BR=16` at two launch
widths) both lost clearly enough, and by enough margin, that further tuning
at the same tile size looked unlikely to close a 27-40% gap. A wider tile is
a different kernel, not a retune, and was out of scope for this round given
the reorder's own win was the safer, already-banked thing to ship.

## Where prefill stands now

Kernel-time reduction from the dispatch reorder alone: 33.04ms -> 23.62ms on
minicpm's pp128 shape, same-session `nsys` trace (-28.5% total, -66.1% on
attention's own share). This is expected to move `pp128`'s throughput
number meaningfully (prefill is far more kernel-time-bound than
launch-bound, unlike decode), but **the `bench.py` confirmation run to turn
that into an actual `t/s` ratio against llama.cpp is the orchestrator's next
step**, per this session's standing rule that only the orchestrator runs
`bench.py`.

Remaining gap after the reorder, from the same trace comparison: phobos's
total prefill kernel time (23.62ms) is still 1.84x llama.cpp's (12.83ms),
down from 2.58x before this beam. The GEMM projection (`q8_qmma` 12.77ms vs
llama's `mul_mat_q` pair 9.91ms, 1.29x) is now the single largest per-kernel
gap in absolute terms, ahead of attention (`attention_block` 4.25ms vs
llama's flash-attention pair 0.74ms, 5.74x) -- attention's *relative* gap to
llama.cpp is still the largest of any kernel family, and is exactly what the
tensor-core attempt tried and failed to close at this tile size. Both are
open leads for a future round; neither was pursued further here given the
correctness-first mandate and the time already spent confirming the
tensor-core path's loss rather than assuming a win.
